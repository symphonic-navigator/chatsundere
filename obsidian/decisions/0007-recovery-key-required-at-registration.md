# ADR 0007: Recovery key generated and shown once at registration

**Date:** 2026-05-18
**Status:** Accepted

## Context

E2EE with a client-held master key has a hard failure mode: losing your only auth method means losing your data, irrecoverably. The server cannot rescue you — that is the point.

Recovery options surveyed:

- **No recovery.** Lose your passphrase / passkey → lose your account. Honest but harsh.
- **Server-side passphrase reset.** Defeats E2EE; rejected.
- **Recovery key.** A 32-byte random key, derived to an AMK, that wraps a copy of the master key. Generated at registration, shown to the user once, stored by them out of band.

The recovery key is itself an auth method: it lives in `auth_methods` alongside `opaque` and `passkey` entries, with its own wrapped master key. The server never sees the plaintext recovery key.

## Decision

A recovery key is **generated and shown to the user exactly once** at the end of every successful initial registration flow (whether the primary method is OPAQUE or Passkey). The user must explicitly confirm they have stored it before they can leave the registration screen.

Format: 32 random bytes, encoded as Crockford base32 in 4-character groups with a checksum character. Example: `K7QW-9X4P-2NM3-…-XX`.

Rules:

- An account cannot exist with **only** a recovery key — at least one non-recovery method must be present first.
- The recovery key can be re-generated by an authenticated user (with another method). Doing so invalidates the previous recovery key. UI warns prominently.
- Recovery flow requires the recovery key to unwrap the master key, then forces the user to establish at least one fresh non-recovery auth method before proceeding.

Server-side proof of successful unwrap during recovery: `mk_proof_value = HMAC-SHA256(MK, "chatsundere-mk-proof-v1")`, stored on the user record at registration time. Client demonstrates knowledge by producing it; server compares.

## Consequences

Positive:
- Users have a self-managed escape hatch without ever giving the server access to plaintext keys.
- No "forgot password" feature is needed, and none should be added.
- Recovery flow is auditable: it logs a `recovery_used` event without leaking any cryptographic material.

Negative / accepted trade-offs:
- User has to store and protect a physical / out-of-band secret. Lose it and your passphrase / passkey → unrecoverable.
- One extra wrapped-master-key column per user. Trivial storage cost.
- Re-establishing fresh auth methods after recovery is mandatory, which adds steps but eliminates the risk of an unauthorised recovery silently leaving stale auth methods in place.
